## v32_Batch32 — 2026-08-10
- **Debug (root cause) + UX polish** (3 files: `ImageCompressor.kt`, `MediaScanner.kt`, `MainActivity.kt`). User uploaded crash log `crash_20260810_134626` + fresh repo zip, asked to focus on debugging + generic-app UX details. Debug Priority followed: crash log analyzed first, no Logcat/ADB needed.
- **OOM crash fix**: the crash's own stack trace (MediaTek `BoostFwk`, a 32-byte allocation) wasn't the cause — just whatever tiny allocation happened to run right after the heap was already full. Real cause: `ImageCompressor.compressInPlace()` decoded JPEGs at full resolution into `ARGB_8888` with zero `BitmapFactory.Options` — a 108MP photo (plausible on the crashed device, Infinix/MediaTek) is a single ~430MB allocation, enough alone to exhaust a 512MB `largeHeap`. Worse, `OutOfMemoryError extends Error` not `Exception`, so the existing `catch (e: Exception)` never caught it — app died outright, matching the log.
- Fix: read bounds first (cheap), fall back to `RGB_565` (half the memory) instead of `ARGB_8888` only above 24MP — keeps the "never downscale resolution" promise for the vast majority of photos, only trims bit-depth for the rare outlier that would otherwise crash. Explicit `catch (e: OutOfMemoryError)` added at both decode and write sites → `Result.Failed` for that one photo instead of taking the whole app down. Same defensive `OutOfMemoryError` catch added to `MediaScanner.decodeSampledBitmap` (blur/near-dup scan path) — not the cause here (already `inSampleSize`-capped), pure hardening against a corrupt header.
- **Polish — success/Undo feedback on destructive actions**: audited all 13 `showSnackbar` call sites — every one was failure-only, zero success confirmation anywhere (permanent delete, organize/move, trash restore, swipe-session commit). Added: "Deleted N photos — freed X MB" (permanent delete, both API 30+ and legacy paths, irreversible so no Undo), "Moved N photos to \<folder\>" (organize, both paths), "N photos restored" (trash restore), and "N photos moved to trash" **with an Undo action** (swipe-session commit — the one reversible case; `trashStore.remove(ids)` is the exact inverse of the `addToTrash(ids)` just performed).
- Confirmed the existing per-swipe "Undo last swipe" button (`SwipeScreen.kt`) is a different, already-correct mechanism (undoes one uncommitted swipe) — left untouched, no overlap with the new session-level Undo.

## v31_Batch31 — 2026-08-10
- **Bug fix — dead-end permission denial** (`MainActivity.kt`, 1 file). Audit finding: `PermissionScreen`'s "Grant access" button just called `permissionLauncher.launch(...)` unconditionally — after a real denial, Android won't re-show the system dialog on a plain re-request, so the button silently did nothing on a second tap, leaving the user stuck with no way forward except uninstalling/reinstalling or knowing to dig into system Settings manually. Classic generic-app gap.
- Fix: after a denial, check `ActivityCompat.shouldShowRequestPermissionRationale` per permission — `false` for a still-ungranted permission right after a request fired is the standard "permanently denied" signal (covers both explicit "Don't ask again" and plain "denied twice" on OEM skins that skip the checkbox). `PermissionScreen` now switches copy + button ("Open Settings" instead of "Grant access") and deep-links to `Settings.ACTION_APPLICATION_DETAILS_SETTINGS` for this app.
- Added an `ON_RESUME` lifecycle observer (same pattern already used for the app-lock re-lock check) so coming back from that Settings screen re-checks permission state immediately — without it, granting access there would still leave the app stuck on `PermissionScreen` until a full relaunch.
